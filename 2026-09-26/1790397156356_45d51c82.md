# 代码评审报告

## 一、变更概述

本次变更为单行修改，位于 `OpenAiCodeReview.java` 的微信模板消息发送逻辑中，将消息接收人 `touser` 从旧值替换为新值：

```java
- message.setTouser("c-dJxoEJSr4kqyqKSvrxYqJ_Xpr4hb3gXZ4ny8WIRaM");
+ message.setTouser("oca1u22ZG_hGaQMrnOUyXRqwO9oM");
```

## 二、变更性质分析

**从格式上看，这是一次疑似缺陷修复：**

| 值 | 特征 | 是否符合公众号 openid 格式 |
|---|---|---|
| 旧值 `c-dJxo...IRaM` | 43 位，`c-` 前缀 | ❌ 不符合 |
| 新值 `oca1u...9oM` | 28 位，`o` 开头 | ✅ 符合标准格式 |

微信公众平台的模板消息要求 `touser` 为标准 openid（28 位、`o` 开头），旧值大概率是**无效 ID**，意味着此前消息一直发送失败（errcode 43003/40003 之类）。**但代码中无响应校验，这个失败很可能一直被静默吞掉了**——这引出了下面的核心问题。

## 三、问题清单

### 🔴 P1-1：配置硬编码（根因问题）

收件人 openid 直接写死在源码里，导致：

- **每次更换接收人都需要改代码、编译、发版**，本次 commit 本身就是这个问题反复出现的证据（这已经是“改人名式提交”）；
- 无法区分环境，SDK 被多人/多项目复用时会互相干扰；
- 个人身份标识被永久写入 Git 历史。

**建议**：外部化到环境变量或配置文件。该 SDK 常配合 GitHub Actions 使用，可用环境变量注入：

```java
private static final String WECHAT_TOUSER =
        Optional.ofNullable(System.getenv("WECHAT_TOUSER"))
                .orElseThrow(() -> new IllegalStateException("缺少配置: WECHAT_TOUSER"));
```

### 🔴 P1-2：发送结果未校验（掩盖了本次要修的 bug）

```java
sendPostRequest(url, JSON.toJSONString(message));  // 返回值被丢弃
```

微信接口会返回 `errcode/errmsg`，不校验则消息发没发成功完全不可知。**本次修复的有效性目前无法被验证**。建议：

```java
String response = sendPostRequest(url, JSON.toJSONString(message));
JSONObject result = JSON.parseObject(response);
if (result.getIntValue("errcode") != 0) {
    log.error("微信模板消息发送失败, touser={}, errcode={}, errmsg={}",
            toUser, result.getIntValue("errcode"), result.getString("errmsg"));
    // 视场景决定：抛异常 / 告警 / 重试
}
```

> 注意：日志中不要打印含 `access_token` 的完整 URL。

### 🟡 P2-1：上下文中可见的其他硬编码

```java
message.putData("project", "big-market");
```

项目名同样写死，SDK 作为中间件应参数化，否则复用到其他仓库时评审报告的项目归属是错的。

### 🟡 P2-2：敏感信息入库意识

openid 本身泄露风险有限（需配合 appid/secret 才能作恶），但这次事件应作为**团队规约**的触发点：`access_token`、`appsecret`、`webhook` 地址等一旦硬编码提交，就必须走密钥轮换流程。建议在 CI 中加入 secret 扫描（如 gitleaks）作为门禁。

### 🟢 P3：结构性建议（非本次必改）

- 多人通知场景下，公众号模板消息 `touser` 仅支持单 openid，需循环发送；若未来需要群发/按人路由，可考虑企业微信（支持 `|` 分隔）；
- 建议将微信推送逻辑抽为独立的 `WeChatTemplateMessageSender`，与本类的“代码评审编排”职责分离，同时便于 mock 测试。

## 四、总结

| 维度 | 评价 |
|---|---|
| 变更意图 | ✅ 正确，修复了无效的收件人 ID |
| 修复方式 | ⚠️ 治标未治本，硬编码模式注定还会出现下一次此类 commit |
| 可观测性 | ❌ 缺失，建议随本次一起补上响应校验与失败日志 |
