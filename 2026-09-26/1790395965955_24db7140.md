# 代码评审报告

## 总体评价

本次变更实现了**企业微信模板消息推送**功能（获取 access_token → 发送模板消息携带 Review 日志链接），功能方向正确，但存在 **2 个必须立即处理的严重问题**（密钥泄漏、疑似复制粘贴 Bug），以及较多设计层面的改进空间。

## 🔴 P0 严重问题（必须修复）

### 1. 微信密钥硬编码并提交到版本库 —— 凭证泄漏

```java
// WXAccessTokenUtils.java
private static final String APPID = "wxfcfc96c8e6814421";
private static final String SECRET = "403c11693161dfb6f693c045419a9568";
```

- 这是**真实的生产凭证泄漏**，且已进入 git 历史，即使后续删除也会被保留。
- **处理措施**：
  1. 立即在微信公众平台**重置 AppSecret**（旧值作废）；
  2. 改为从环境变量/配置中心读取（项目中 githubToken 已是外部传入，应保持一致风格）：

```java
private static final String APPID = System.getenv("WX_APPID");
private static final String SECRET = System.getenv("WX_SECRET");

static {
    if (APPID == null || SECRET == null) {
        throw new IllegalStateException("缺少微信配置：请设置 WX_APPID / WX_SECRET 环境变量");
    }
}
```

### 2. `touser` 与 `template_id` 写反了 —— 功能性 Bug

```java
// OpenAiCodeReview.java
message.setTouser("c-dJxoEJSr4kqyqKSvrxYqJ_Xpr4hb3gXZ4ny8WIRaM");
```

对照 `Model.Message` 的默认值：

```java
private String touser      = "oca1u22ZG_hGaQMrnOUyXRqwO9oM";           // 这才是 openid
private String template_id = "c-dJxoEJSr4kqyqKSvrxYqJ_Xpr4hb3gXZ4ny8WIRaM"; // 模板ID
```

`setTouser()` 传入的实际上是 **template_id**，微信会返回 `errcode 40003 (invalid openid)`，**推送必然失败**。此处要么删掉这行（Message 已有默认 touser），要么传正确的 openid。

### 3. 测试"由红改绿"方式可疑

```java
- System.out.println(Integer.parseInt("000SHI"));
+ System.out.println(Integer.parseInt("00999"));
```

原测试因 `"000SHI"` 无法解析而失败，现在改输入让它通过——这是**掩盖问题而非修复问题**。需要确认：这个测试的初衷是什么？是否曾有其他用例依赖该行为？同时该测试没有任何断言，只是打印，**不具备回归保护能力**：

```java
Assert.assertEquals(999, Integer.parseInt("00999"));
```

## 🟠 P1 重要问题

### 4. `Message` 类放在 `Model` 枚举内部 —— 设计错位

`Model` 是 AI 模型枚举（gpt-3.5 等），把微信消息 DTO 作为其静态内部类违反单一职责，且与测试中又复制了一份 `Message` 形成**三处重复**（Model.Message / ApiTest.Message / 未来可能还有）。建议：

- 独立为 `domain/model/WxTemplateMessage.java`；
- 测试直接复用该类；
- 字段命名遵循驼峰，fastjson 序列化用注解映射：

```java
public class WxTemplateMessage {
    private String touser;
    @JSONField(name = "template_id")
    private String templateId;
    private String url;
    private Map<String, Map<String, String>> data = new HashMap<>();
    // ...
}
```

### 5. 双括号初始化反模式

```java
data.put(key, new HashMap<String, String>() {{
    put("value", value);
}});
```

匿名内部类会持有外部类引用（潜在内存泄漏）、序列化行为脆弱。直接：

```java
public void putData(String key, String value) {
    data.put(key, Map.of("value", value));
}
```

### 6. Access Token 无缓存 —— 会被微信限流

`expires_in` 解析了却从未使用。微信 access_token 有效期 7200 秒，且有每日获取次数上限。CI 每次构建都请求一次，很快会撞限额。建议加缓存：

```java
private static volatile String cachedToken;
private static volatile long expireAt;

public static synchronized String getAccessToken() {
    if (cachedToken != null && System.currentTimeMillis() < expireAt - 60_000) {
        return cachedToken;
    }
    Token token = fetchToken(APPID, SECRET);
    cachedToken = token.getAccess_token();
    expireAt = System.currentTimeMillis() + token.getExpires_in() * 1000L;
    return cachedToken;
}
```

### 7. 异常处理与资源管理缺陷

```java
} catch (Exception e) {
    e.printStackTrace();   // 吞掉异常返回 null
    return null;
}
```

- 返回 `null` 后，`pushMessage` 里会拼出 `access_token=null` 的 URL，报错信息面目全非。**应抛出非受检异常快速失败**；
- `BufferedReader` 未用 try-with-resources 关闭；
- `HttpURLConnection` **未设置超时**，网络抖动时整个流程可能无限挂起：

```java
connection.setConnectTimeout(5_000);
connection.setReadTimeout(10_000);
```

- 微信业务错误返回 HTTP 200 + `errcode != 0`，当前只判断了 HTTP 状态码，需额外解析响应体中的 `errcode/errmsg`。

### 8. 硬编码的默认值不可靠

```java
private String url = "https://github.com/.../2026-09-26/1790391932405_62790ffd.md";
```

默认值指向一条**具体的、日期还是未来的**历史日志，作为兜底值会产生误导（消息跳错页面）。应默认为 `null`，由调用方显式赋值。同理 `message.putData("project", "big-market")` 中项目名也应随上下文传入而非写死。

## 🟡 P2 建议改进

| 项 | 说明 |
|---|---|
| 参数命名 | `getAccessToken(String APPID, String SECRET)` 参数名全大写违反 Java 规范，应为 `appId/secret` |
| 日志 | 全部使用 `System.out.println`，SDK 类库建议引入 SLF4J 门面 |
| 测试外部依赖 | `test_wx` 直连真实微信 API，会导致 CI 不稳定、消耗配额，建议打上 `@Ignore` 或拆分集成测试目录 |
| 代码重复 | 测试类中的 `sendPostRequest` 与主流程逻辑重复，应下沉到 utils 复用 |
| 文件规范 | `Model.java` 缺少文件末尾换行（`\ No newline at end of file`） |
| `Token` 内部类 | 字段 `access_token` 下划线命名，可加 `@JSONField(name="access_token")` 改为驼峰 |

## 架构层面建议

当前 `OpenAiCodeReview` 是一个"上帝方法"：执行 Review → 写日志 → 推送通知全部内联。建议做如下演进，为后续扩展（钉钉、飞书、邮件等通知渠道）留出扩展点：

```
OpenAiCodeReview (编排层)
   ├── CodeReviewService   —— 调用 OpenAI 生成评审
   ├── LogWriter           —— 写入 GitHub 仓库，返回 logUrl
   └── MessageSender (接口)
          └── WxTemplateSender —— 微信模板消息实现（配置来自 WxProperties）
```
